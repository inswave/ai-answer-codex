구조 요약

API 서버는 요청을 받고 결과를 돌려주는 역할만 맡습니다. 답변을 만드는 과정은 AnswerPipeline에 모았습니다. 검색은 Python RAG 서버로 분리했고, 수집/분류/인덱싱은 답변 요청과 따로 돌리는 배치 작업으로 구성했습니다.

문의 처리 경로
고객 문의 → Express API → Answer Pipeline → RAG/MCP/OCR/LLM → API 검증 → 답변/출처/검토상태 반환
데이터 갱신 경로
수집원 → raw 저장 → 통합/분류 → 임베딩 생성 → ChromaDB 저장 → 검색 서버에서 사용

수집 계층
src/collectors/index.js에서 수집기를 실행합니다. 대상은 Gmail, W-Tech, Confluence, API Guide, W-Tech FAQ입니다. Puppeteer를 사용할 수 없는 서버에서는 W-Tech 계열 수집을 건너뛸 수 있습니다.
정제/분류 계층
수집 결과를 통합 Q&A로 합치고 문의 유형별 카테고리를 붙입니다. 이 결과가 검색 인덱스의 문서 본문과 메타데이터로 들어갑니다.
검색 계층
searcher.py는 벡터 검색과 BM25 검색을 같이 수행합니다. 최종 점수는 벡터 0.6, BM25 0.4 가중치로 합산하고, 상위 결과만 답변 컨텍스트로 넘깁니다.
항목설계비고
임베딩 모델 intfloat/multilingual-e5-base 문서 passage:, 질의 query: prefix 사용
벡터 저장소 ChromaDB PersistentClient / Q&A 검색 컬렉션 data/chroma에 저장
인덱싱 내용 기반 doc_id, batch 256, 증분 upsert --reset으로 전체 재색인 가능
검색 서버 127.0.0.1:8765 HTTP 서버 모델과 BM25 인덱스 상주, 장애 시 subprocess 대체
성능 구조

질문마다 임베딩 모델을 새로 로딩하면 응답이 늦어집니다. 그래서 RAG 서버를 별도 프로세스로 띄워 모델과 BM25 인덱스를 메모리에 올려 둡니다. 첫 기동은 시간이 걸리지만, 운영 중 검색 응답 시간은 줄어듭니다.

보안 및 장애 대응

인증/권한
/api/answer는 API Key 인증을 적용합니다. 운영 설정은 config/config.json으로 분리합니다.
민감정보
로그와 답변 저장 전에 masking.js가 고객명, 이메일, 전화번호 등 민감 패턴을 제거합니다.
Fallback
RAG 서버 장애 시 subprocess 검색으로 대체합니다. LLM 실패는 API 오류와 로그로 남깁니다.
장애 시나리오처리 방식확인 위치
RAG 서버 미응답 파이프라인이 Python subprocess 검색으로 자동 대체 API 서버 로그, RAG 서버 로그
Codex Exec timeout / quota 답변 API 실패 응답 반환 서버 stderr, 운영 감시 로그
OCR 실패 첨부 컨텍스트 없이 RAG/MCP 중심 답변 생성 파이프라인 attachment summary
미검증 API명 발견 1회 재생성 후 남은 항목은 경고로 표시 apiVerifier.js 결과
본 문서는 현재 구현 기준으로 작성했습니다. 계정, 내부 URL, API Key 등 보안 정보는 포함하지 않았습니다.
